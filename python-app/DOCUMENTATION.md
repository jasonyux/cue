# Python App Documentation

Reference material for the Python backend. The [README](README.md) is the short version; this page holds the details, organized by feature.

## Entry Points and Request Flow

`pnpm cue web` (or `pnpm cue dev`, with the console's dev server) runs `scripts/launch.mjs` at the repository root, which starts the Next.js console (port 3000) and this backend (port 4041) and holds a pipe to the backend so closing the launcher shuts it down cleanly.

**Backend process.** `app/__main__.py` loads `.env` from the repository root (the providers' keys and base URLs; a variable the backend started with wins over the file, and the launcher passes it only the shell's; `load_environment` in `app/config.py`, which the settings page's Save and every opening of that page run again), builds `Settings` (`app/config.py`: data root, default model, host, port), and serves the FastAPI app from `create_app` in `app/api.py`. That file declares the scenario and run routes and registers the live-session routes from `app/live/api.py`. Two long-lived objects hang off the app: `RunnerManager` and `LiveSessionManager`.

**A task run.** `POST /api/runs` → `RunnerManager.start_run` (`app/runner.py`), which owns admission (one run at a time), the run record, events, and artifacts. Execution is `execute_scenario` in `app/scenario_runtime.py`: it spawns the per-run worker subprocess (`app/desktop/worker.py`, managed by `app/desktop/runtime.py`), wraps it in a `DesktopSession` (`app/desktop/ax/session.py`) or a browser session, and hands off to `run_responses_code_loop` in `app/responses_loop.py`. That loop is the model conversation: each turn the model emits `exec_py` code, the worker runs it, and the output returns as the next `function_call_output`. Inside the worker, the `ax` object the model calls is `AccessibilityDesktop` in `app/desktop/ax/client.py`; `tree.py` serializes accessibility trees, `keys.py` maps key chords, `capture.py` takes screenshots.

**A continuous session.** `POST /api/live/session` → `LiveSessionManager.start` (`app/live/session.py`), the orchestrator. The package is organized by pipeline stage, and data flows one way through it; a later stage may import an earlier one, never the reverse:

When a run is started with live context, the run manager asks the session manager for what the session shows the run (its worklog and latest proposal) and for the folder to store the run in; both come from `actor/session_runs.py`.

**Console.** `console/app/page.tsx` renders the session console (`console/components/live/LiveConsole.tsx`) for the Python backend. It talks to the backend over HTTP and validates responses against the zod schemas in `contracts/index.ts`, which `app/models.py` mirrors with Pydantic.

## Run Artifacts

Each run directory holds `run.json`, `replay.json`, `events.jsonl`, `screenshots/`, and `model_calls.jsonl`, the raw Responses API request and response per turn (inline images summarized unless `CUA_LOG_MODEL_IMAGES=1`). `run.json` carries a `usage` block: calls, input, cached, cache-write, output, and reasoning tokens, per model and in total, plus an estimated `costUsd` when `app/configs/model_prices.json` or the `CUA_MODEL_PRICES` JSON environment override lists a price for the model. Runs started from a continuous session also store `live_context.md`, the observed context appended to their instructions.

Standalone runs live under `data/runs/<run id>/`; runs started from a session live under `data/sessions/<session>/runs/<run id>/`. `RunStorage` (`app/storage.py`) finds either place, including after a restart.

Desktop runs capture a timeline frame before the model has observed any window. That frame is a stand-in image and is flagged `placeholder: true` on its screenshot record (`app/desktop/placeholder.py` owns what it is and how it is recognized); the session console skips such frames.

## Accessibility Control Mode (macOS)

`CUA_DESKTOP_MODE=accessibility` replaces PyAutoGUI in the worker with an `ax` object (`app/desktop/ax/`):

- `ax.get_state(app)` resolves the app (name, bundle id, or pid; launched if needed), reads its key window, and returns an `AppState`: an indexed accessibility tree (`[index] role "title" value` lines, window-relative frames) plus a screenshot of that window only. The window is resolved from the accessibility element through the private `_AXUIElementGetWindow` call, with a frame-and-title match among the app's on-screen windows as the fallback; the capture uses ScreenCaptureKit, so it works while other windows cover it. A failed screenshot is noted in the state header rather than failing the call.
- `ax.click(app, index)`, `ax.double_click`, `ax.right_click`, `ax.focus`, `ax.set_value(app, index, text)`, `ax.actions`, and `ax.perform_action` act on tree elements through accessibility actions. `ax.type_text`, `ax.press_key(app, chord)`, `ax.scroll`, `ax.drag`, and coordinate clicks post events to the target process only.
- Chromium, Electron, and WebKit apps expose their trees only after a client asks; the client switches that on.
- Nothing moves the system pointer or changes the frontmost app. The two scenarios (`app/desktop/ax/scenarios.json`) operate local apps.
- The tool guidance (`code_tool_guidance` in `app/responses_loop.py`) tells the model to prefer the tree and fall back to screenshots and coordinates for apps that draw their own controls.
- A native crash in the worker (a macOS framework assertion) is reported with the worker's stderr tail and Python stack in the run's failure event.

## Continuous Sessions

### Pipeline

1. **Recorder** (`observer/recorder.py`, a subprocess, reading the screen through `observer/sources.py`): every `observer.snapshot_interval_s` seconds it records the frontmost app, the focused window's accessibility tree, the window under the pointer when that differs, and the titles of the other windows on screen, into `snapshots.jsonl`. Identical ticks collapse into `screen_unchanged` rows. The console's own window (titled Cue Console, or ComputerPilot Console as an app installed under the earlier name still is; as a tab or an installed web app) is never a look: nothing is recorded while it is in front, and it is never asked about. When the rules change while the latest look is a stub (an answer on the console, a saved rule), the next look, within half a second, is at that app by its pid wherever its window is, with the window's own pixels rather than a display cut: the monitor shows the app the answer was about, or its stub with the new reason. Screenshots are cut from the display at the focused window's frame, so they show what you see there, overlapping windows and pointer included; they are saved on each app switch by default, on every distinct snapshot when a model loop wants images, or never. The observer keeps recording while a task run is active: the agent works in background windows, so what the observer sees stays yours.
2. **Digest** (`observer/digest.py`, pure functions): turns a batch of snapshots into readable text (app and window switches, dwell times, tree excerpts that put typed and focused elements first) and turns summaries into the context block a task run receives.
3. **Summarizer** (`observer/summarize.py`): every `summary.interval_s` seconds, the digest of the new snapshots becomes one worklog line in `summaries.jsonl`. Thinking off by default. With screenshots enabled, the two newest captures ride along as images (`utils/images.py` downscales them to `screenshotMaxSide`), which covers apps that hide their text from the accessibility tree, such as editors and terminals. Windows with nothing but pause markers make no model call.
4. **Belief updater** (`belief/update.py`): every `belief.interval_s` seconds, the task list as the stream last carried it with the ops since replayed (open entries with the date they were added), the last `belief.context_summaries` worklog lines before the update for the arc of the work, the person's preferences file when it has any (`data/memory/preferences.md`, pipeline step 8, shown first), and the worklog lines every session has written to the stream since the last update (its cursor, `streamCursor` in `data/memory/tasks.json`) become add / update / done operations; `MemoryStore.apply` applies them under its rules and the resulting list is also appended to the session's `beliefs.jsonl` and to the stream. Its cursor lives in memory, not the session, so lines left over when a session stops are folded in at the next session's first tick.
5. **Proposer** (`proposer/propose.py`): every `proposer.interval_s` seconds, the task list, the worklog, the digest of the raw recent observations, and the current window's tree, any subset of them per `proposer.inputs`, become a proposal set in `proposals.jsonl`. The prompt covers three kinds of help (`explain` something on screen, `lookup` information the person needs next, `act` with the agent's hands), says that explanations and lookups are what people want most, lists cues that someone is stuck, and treats a missed moment as worse than a declined offer. When a task run is in progress, its prompt is listed so the proposer does not propose it again. With the `feedback` source on, the prompt also lists the person's last `proposer.feedback_window.rejected` rejected and `.accepted` accepted proposals across sessions, each with a digest of what the proposer saw at the time, and the top proposal of the last `.recent` rounds of this session nobody has answered yet, as their preferences; the prompt says nothing about what to do with them.
6. **Duplicate filter** (`proposer/dedup.py`, on with `proposer.dedup`): the guardrail between the proposer's reply and everything downstream; the prompt is untouched. Each new proposal is embedded (`utils/embed.py`, an OpenAI-compatible `/v1/embeddings` endpoint, `embed.model` / `embed.base_url` / `CUA_EMBED_API_KEY`) and compared by cosine with three kinds of reference: every accepted or rejected proposal in `data/memory/feedback.jsonl`, any age, except "not now" rejections; "not now" rejections from the last `proposer.dedup_not_now_hours`; and every proposal this session made in the last `proposer.dedup_session_hours`, decided or not. At or above `proposer.dedup_threshold` the proposal moves from `proposals` to `filtered` on the record, with its `score`, the reference text it `matched`, its `source` (`decision`, `not_now`, `session`) and a `note` ("accepted 2026-10-05", "proposed 14:27 this session"); the flat top fields follow the first proposal left and `action` is `none` when none is, so nothing is notified. The console shows "2 filtered as duplicates (0.91, 0.84)" under the round, the proposals themselves on demand. Vectors are cached in `data/memory/embeddings.jsonl`, one row per (model, text), so a text is embedded once ever; each embeddings request is one `live_model_calls.jsonl` row of kind `embedding`, its usage goes on the round's record as `embedding: {model, usage}` and into the session's totals, and the cost panel lists it as `proposer: duplicate filter` (and `belief updater: lookalike check`, the belief updater's embeddings calls the same way) (`storage/usage.py`); `text-embedding-3-small`/`-large` are priced in `app/configs/model_prices.json`, with and without the `openai/` prefix OpenRouter uses. A round whose texts were all cached makes no request and records no usage. The "not now" preset, like the other one-click reasons, is `REJECT_REASONS` in `storage/feedback.py`, served to the console as `rejectReasons` with the defaults, so the list lives in one place. On one real session (27 rounds, 81 proposals) the filter at 0.8 held back 35, all repeats of earlier rounds or of decided proposals.
7. **Notify** (`proposer/notify.py`): nothing is executed from a proposal set. The top proposal is surfaced as a macOS notification (when `notify` is on) and in the console, and the record's `effect` says which happened.
8. **Preference updater** (`preference/update.py`): a tick every `preference.interval_s` while a session runs and one more at its stop, each run only when at least `preference.min_feedback` reactions wait (a decision on a proposal with its digest and any reason given later; a thumbs up or down on a task or an entry); fewer stay pending for the next tick, so the model reads a batch rather than one reaction at a time. It reads the reactions since its cursor (kept in `data/memory/preferences.json`, so a reaction between sessions, a thumbs or a decision on a stored session, waits the same way for the next tick that runs), the file as it stands, the last `preference.context_decisions` decisions, the task list, the last `preference.context_summaries` worklog lines and this session's last hour of chat, and is given two tools: `search_history` (up to `preference.search_rounds` searches; the prompt points it at the chat, where the person says most about what they want) and `write_preferences`, which replaces the whole of `data/memory/preferences.md`. A write over `preference.cap_tokens` (`cl100k_base`) is rejected with how much to cut and the model replies again, up to `MAX_ROUNDS` (4) replies beyond its searches; a reply with no write call leaves the file as it is, the usual outcome, since a few reactions are rarely a rule. Each tick is one row in the session's `preferences.jsonl` and a `preferences_updated` event (the file before and after, `changed`, the reactions' ids, the searches, the rejected writes), its calls logged as kind `preference`, its cost under "preference updater". The file is prose rules the proposer can act on, each with where it comes from; the proposer's `preferences` input (both the timer's and the idle trigger's) and a run's live context (`actor/prompts.py`) carry it when it has any. Nothing shows it in the console yet: edit `data/memory/preferences.md` by hand if you like.

The three model loops share `ModelLoop` in `model_loop.py`: a cursor into the stream (this session's observer rows for the summarizer and the proposer, every session's summaries and this session's chat turns for the belief updater), a `Window` over the stream from the first new event to now that each stage pulls its inputs from (`storage/stream.py`: the observations, the worklog before the end, the task list as last carried, the decisions with their digests, the undecided rounds, the runs in progress, the chat's recent turns), usage accounting, screenshot selection, and the truncation fallback. If a thinking call spends its whole output budget reasoning and returns no answer, the same request is retried once without thinking; the record is marked `fallback: thinking_truncated` and the cut-off attempt stays in `live_model_calls.jsonl` as kind `summary_truncated` or `proposer_truncated`.

### Settings

All in `LiveSettings` (`app/live/config.py`). Each has a default, a place in `settings.yaml` at the repository root (`PLACES`: its section and key, the first column below; the repository's `settings.yaml` lists every one, with a comment), and a camelCase key for the start request (`POST /api/live/session`); `wire()` is the shape the console and `session.json` see. API keys are never exposed and never in `settings.yaml`: the providers' key sets (`OPENAI_API_KEY` / `OPENAI_BASE_URL` and so on, `PROVIDER_KEYS`) live in `.env`, so nothing is set in two places. The settings page's Save sends the same keys to `POST /api/live/settings`, which writes a provider's key or base URL to `.env` and everything else to its place in `settings.yaml` (ruamel.yaml's round trip keeps its comments) and reads both again as the defaults of the next session.

### Records and Strategies

Every record that crosses a stage boundary or lands on disk is a model in `app/live/storage/records.py`: `Snapshot`, `Summary`, `Proposal` and `ProposalSet`, `ProposalFeedback`, `SummaryFeedback`, `RunMarker`, `ModelCall`. They validate on read (`parse_stored`), so a stage that writes a wrong shape fails at the file boundary instead of corrupting the next stage, and `wire()` is the camelCase form the files and the console use. Older stored records (a single flat task instead of ranked proposals) are lifted to the current shape on read.

Each model loop separates plumbing from the decisions that make it a summarizer or a proposer. The plumbing is `ModelLoop` in `app/live/model_loop.py`: its shared `tick` reads the new snapshots since the last tick and hands them to the stage's own `run_window`, written out top to bottom in `observer/summarize.py` and `proposer/propose.py` (gather the inputs, ask the strategy for the messages, call the model, parse, write); the model call with its log and truncation retry, and the writing of the record, are helpers on the base class. What a stage actually asks and how it reads the answer is a `Strategy`, two pure methods:

```python
class Strategy(Protocol[I, R]):
    def messages(self, inputs: I) -> list[dict[str, Any]]: ...   # the chat messages for this window
    def parse(self, reply: ModelReply, inputs: I) -> R: ...      # the reply → the record
```

Both inputs are `StageInput` dataclasses (`model_loop.py`), typed by what the stage is shown in `input`. The summarizer's inputs are an `ObservationWindow` (`StageInput[list[Snapshot]]`: the new snapshots, plus the previous worklog lines and the selected screenshots) and its record a `Summary`; the default strategy is `WorklogSummaryStrategy` in `observer/summarize.py`. The proposer's inputs are a `ProposerInput` (`StageInput[ProposerObservations]`: a dict keyed by source, `tasks`, `worklog`, `snapshots`, `current_window`, `feedback`, plus the tasks already running and the proposal cap) and its record a `ProposalSet`; the default is `RankedProposalsStrategy` in `proposer/propose.py`. Which keys the dict has is the `proposerInputs` setting (`proposer.inputs`, any subset of `tasks`, `worklog`, `snapshots`, `current_window`, `feedback`), set in the environment or on the start form: the worklog lines, the window's raw rows, the newest readable row, the recent decisions. The strategy renders a section for each key it finds; screenshots have their own flag. An ablation of the proposer's input is therefore a setting rather than a new strategy, and the session's `session.json` records which variant ran. To experiment with a different way to summarize or propose, write a class with those two methods and pass it as `strategy=` to `Summarizer` or `Proposer` in `session.py`, or replay it over a stored session first (below).

### Replaying a Stage Offline

```
uv run --project python-app python -m app.live.replay --session python-app/data/sessions/<id> --stage proposer [--limit N] [--out DIR]
```

Runs the summarizer or the proposer again over every window the stored session produced a record for, configured by `settings.yaml` and `.env`, the same files a live session reads, so there is one place to change what a replay does; its `replay.json` records the settings it ran with. Nothing in the session folder changes: the new records and model calls go to `<session>/replays/<stamp>-<stage>/` (or `--out`), with a `replay.json` naming the strategy, the settings, and the usage. The summarizer sees its own replayed worklog as context, so a new summarizer is proposed on its own output; the proposer sees the session's stored worklog and the tasks that were in progress at each window's end. The command ends by printing the stored and replayed records side by side, which turns "is my summarizer better" into a comparison over the same data instead of a fresh live session.

### Model Output and Records

The summarizer answers `{"summary": str}`. Its record in `summaries.jsonl`: `ts`, `windowStart`, `windowEnd`, `summary`, `observations`, `model`, `usage`, `images`, and `fallback` when the truncation fallback fired.

The proposer answers `{"summary": str, "proposals": [{"kind", "task", "reason", "confidence"}]}`, best first. The prompt asks for two sorts of proposal: help with what is on screen when the person looks stuck, and moves that carry a task forward beyond the screen (a pending checklist entry they are not on right now, a next step or feature toward a goal, a task gone quiet), with at least one of the latter whenever the task list has pending entries. `confidence` is a 1-5 Likert score (5: sure the person will accept, 1: a long shot), 0 when the model gave none; the console shows it as n/5. `ProposalSet.from_model_output` in `storage/records.py` types every field (the score is clamped to 1-5), drops proposals without a task or with a duplicate task, caps the list, and mirrors the top proposal in flat `kind`/`task`/`reason`/`confidence` fields; `action` is `propose` when there is at least one proposal and `none` otherwise (the run context and the policy key off it). The record in `proposals.jsonl` adds `ts`, `windowStart`, `windowEnd`, `observations`, `model`, `usage`, `images`, `reasoning` (first 4000 characters), `effect` (`recorded`, `proposed`, or `notified`), and `fallback` when it applies. A response that is not a JSON object is recorded as `action: none` with the raw text under `raw`.

Each task is a numbered checklist of steps, pending or done with a date. The belief updater is given four tools as Chat Completions function schemas with `tool_choice` auto, each doing one thing: `add_task` (title, `steps` as `{text, done}` entries, evidence), `update_task_checklist` (task_id, `add` entries, `remove` entry numbers, `reword` `{step, text}` pairs for open entries, evidence), `toggle_task_status` (task_id, optional `step` number, `done`, evidence; without a step it sets the whole task) `rename_task` (task_id, title, evidence) and `delete_task` (task_id, evidence). Every call becomes one op, several calls in one reply are applied in order with entry numbers resolved against the list as it was shown, and a reply with no calls means nothing changed. Each call first passes `belief/tools.py`'s `check`, applied whole or rejected whole: an unknown tool, a missing argument, a task id not on the list, or text over the length limit is rejected, and the rejection says why (`The entry "…" is 21 words / 30 tokens; the limit is 10 words or 20 tokens. Shorten it by 11 words (10 tokens).`). A title passes when it fits in 7 words or 15 `cl100k_base` tokens, an entry in 10 words or 20 tokens (`TITLE_LIMIT`, `ENTRY_LIMIT`, constants). After the check, a call that adds an entry or a task is held back once when what it adds embeds at or above `belief.similar_threshold` against an entry or title on the list: its result names the lookalikes with their state (`Warning, not applied: "…" is close to entry 8 of t001 "…" (open since 2026-10-20) …`), and the same call again is applied (`BeliefUpdater.lookalikes`; the warnings are the record's `warned`). Entries carry `addedAt`, shown as `(added …)` on open entries; `python -m app.live.storage.backfill_added --data-root data --write` dates older entries from the call that added them, with the backend stopped; tokens catch detail-stuffing (hostnames, ids, paths) that few words hide, words leave room for a plain phrase. Accepted calls are applied at once; when a reply had a rejected call, the model gets every call's result back as `tool` messages and replies again, up to `MAX_ROUNDS` (4) replies per tick, so a tick where everything passes stays one call. Each reply is one row in `live_model_calls.jsonl`; the record carries the rounds' total `usage`, `rounds`, and the `rejected` results. There is no limit on how many tasks can be active. `MemoryStore.apply` gives each new task a random short id (`t` and 8 hex characters; tasks from before keep `t001`, …), so an id is never reused, skips duplicate steps, revives a paused task on update, pauses active tasks not seen for `belief.stale_days`, keeps finished steps for good (the console hides those older than `belief.done_step_days`), keeps each checklist ordered pending-first then finished newest-first, and never deletes outright: `delete_task` and removed entries go to a trash, hidden from the list and the prompt but kept in `tasks.json` with a `deletedAt`, restorable by the operator until `belief.trash_days` have passed. The record in `beliefs.jsonl` holds the ops and the task list after them. Parsed tool calls are a server feature on vLLM (`--enable-auto-tool-choice --tool-call-parser hermes` for Qwen); the Test configuration button probes for them on the belief updater's endpoint.

Model calls are not retried by the SDK: a call that exceeds the client timeout (300 s) is recorded as that tick's error and the loop moves on; while a tick is running, its `next…At` in the status payload is null and the console shows "running now". Every model request and response, for all three roles, is appended to `live_model_calls.jsonl` with `kind`, `windowStart`, and `windowEnd`, so any summary or proposal set can be traced to its exact call.

### Console Interactions and Feedback

- **Accept** copies the chosen proposal into the one-shot task box (→ One-shot task) or into the chat box (→ Chat), picked from the menu the button opens on hover; nothing runs. **Reject** dismisses the whole proposal set. **See other choices** unfolds the lower-ranked proposals, each with its own Accept, so picking the second or third is recorded as a disagreement with the ranking. Recording a decision returns at once and then makes one model call in the background: the proposer's exact input for that round is read back from `live_model_calls.jsonl` (its text without the closing instruction, plus the same screenshots re-encoded from the session's folder) and condensed to at most 50 words by the proposer's own endpoint (`proposer/feedback_digest.py`; the running session's client, or one on the default proposer endpoint when labeling a stored session), logged there with kind `proposer_feedback` and shown in the cost panel as `proposer: feedback digest`. The record in `feedback.jsonl`: `ts`, `proposalsTs`, `decision`, `choice` (0-based index, null for reject), the chosen `kind`/`task`/`reason`/`confidence`, all `proposals` that were offered, `context` (that text, written onto the row when the digest lands; `digestError` instead when it fails), and the digest call's `model` and `usage`. The console shows "digesting…" next to a decision until then, and a session's teardown waits for digests in flight before closing its clients. A copy with `ts`, `sessionId`, `decision`, `kind`, `task` and `context` goes to `data/memory/feedback.jsonl`, the proposer's `feedback` source. After a Reject the console offers a reason, optional and one click: `already done`, `not now`, `do it myself`, `not useful`, or a few typed words; `POST /api/live/session/proposals/feedback/reason` (and the same under `/api/live/sessions/{id}/`) with `{proposalsTs, reason, typed}` writes it as `rejectReason` plus `reasonTyped` (true when it came from the "other…" prompt, false from a preset button) onto that decision's row and its memory note, and the stream's `reject_reason_given` event carries the same as `typed`; the proposer's line then reads `rejected, not now (kind): …`. The feedback source orders by it: of the last `proposer.feedback_window` rejections it shows the latest typed ones first and fills with the latest others, so the person's own words outlive a run of preset clicks. The latest decision per proposal set is what the console shows. Accepting a proposal set that has no proposals is refused; a proposal set with no logged request can be decided, but its digest fails and the row says so.
- **Flag** on a summary takes an optional note on what went wrong. The record in `summary_feedback.jsonl`: `ts`, `summaryTs`, `verdict` (`wrong` or `ok`), `comment`, `windowStart`, `windowEnd`, `summary`, `model`, `images`, `observations`; the matching model call has kind `summary` and the same `windowEnd`.
- The history view lists earlier sessions; feedback there records labels the same way, and nothing can be run from it.

### Task Runs From a Session

A run started from the live page (the request carries `liveContext: true`) is executed by the live actor in `app/live/actor/`: `scenario_runtime.execute_scenario` hands it to `actor/run.py` and does nothing else for it. `run_task` builds the run's `ActorInput` and hands it to the agent the run names: `desktop/run.py` starts the worker(s) and the desktop session and runs `desktop/agent_loop.py` with the tools from `desktop/tools.py`, copies of the scenario page's `responses_loop.py` and catalog text; `cmux/run.py` is described below. The scenario page keeps the originals, so the actor can change tools and instructions without affecting `/scenarios`; the run lifecycle, storage, and event kinds are shared, so the console's run view and replay read both. The actor also has its own copy of the desktop worker and its runtime (`live/actor/desktop/`), where a cell yields: the worker emits every `log()`/`display()` item as it happens, and `exec_py` follows the cell for the session's `actorYieldS` setting (`actor.yield_s`, default 20) and then returns the output so far with a cell id if the code is still running. `wait_cell(cell, timeout_s)` relays further output or the completion, `stop_cell(cell)` sends the worker `SIGINT` (the cell's partial output and traceback come back; globals survive), one cell runs at a time, each progress item is a `tool_progress` run event so the run view shows it live, and a cell still running when the model answers is stopped. Nothing in the instructions tells the model how to structure its work.

With `remote` in `actor.desktop_source`, a live run connects a remote desktop as well as, or instead of, the local worker (`live/actor/desktop/remote.py` picks the provider; `cua/` is the first: `server.py` runs in the container and bridges one WebSocket to a fresh copy of the same `worker.py`, `client.py` gives the actor a `RemoteRuntime` with the local runtime's cell interface). `exec_py` then takes `target`, `local` or `remote`, described to the model as the user's own desktop versus an isolated Ubuntu desktop with its own browser and none of the user's files or accounts, pyautogui and screenshots only; the model chooses per call. Remote cell ids start with `r`, one cell runs at a time across both desktops, `wait_cell` and `stop_cell` work the same (the interrupt is a message the bridge turns into `SIGINT`), and the timeline screenshot after a remote cell comes from that desktop. The run closes the connection, which kills the remote worker. Without the setting nothing changes.

With `cmux` among `actor.agents`, a run can be handed to Claude Code instead (`agent: "cmux"` on the start request, recorded as `actorAgent` on the run detail). `execute_scenario` then starts no worker and no desktop session and calls `live/actor/cmux/run.py`: it writes the run's prompt, the instructions (the cmux agent's text from `prompts.py`, then the observed context) and a launcher script into the run's `cmux/` folder, has cmux open a background workspace whose process is the script (`cmux rpc workspace.create` with `initial_command`: the script runs in place of the interactive shell, so a prompt at shell startup such as oh-my-zsh's update question cannot hold it up), and closes that workspace when the run is stopped, which also ends Claude; a workspace whose script has ended closes itself. Inside a cmux workspace `claude` is cmux's wrapper, which brings cmux's computer-use tools next to Claude's shell, file and web tools. cmux's built-in browser is available to it as well (`cmux browser …`, a Playwright-like CLI: `open`, `snapshot --interactive`, `click`, `type`, `wait`, `eval`, profiles with their own cookies); the cmux agent's instructions prefer it for web pages, in an `agent` profile and in the session's **agent browser workspace** (`cmux/browser.py`: one workspace titled so, found or created on the first cmux run and closed when the session stops, its ref handed to Claude as `CUA_ACTOR_CMUX_BROWSER_WORKSPACE` and recorded as `actorCmuxBrowserWorkspace` on the run detail), so pages outlive the turn and the user can watch or step in; after every shell step that touched the browser, `events.py` screenshots each page in that workspace (`cmux tree`, `cmux browser screenshot`) onto the run. The user's own browser is left for their logged-in accounts. Claude learns its commands from cmux's `cmux-browser` skill, vendored in `app/live/actor/cmux/skills/` and installed into `~/.claude/skills/` by `pnpm cmux:skills`, which also creates the profile. The script runs `claude -p --output-format stream-json --verbose --include-hook-events --max-turns <the run's turn budget> --append-system-prompt-file cmux/instructions.md` with the prompt on stdin and the stream written to `cmux/stream.jsonl`, so the instructions are added to Claude Code's own system prompt the way the desktop agent's are sent as its instructions; `run.py` tails that file, so Claude is never a child of the backend, and `events.py` turns each line into the run events the console already renders: the session's first line (model, permission mode, tools, connected servers; the run record takes its model from it; a first line without any `mcp__cmux-cua__` tool adds a warning, since cmux's wrapper attaches computer use only when it finds its auth token, which macOS's daily temp-folder cleanup deletes once cmux has run for three days — restarting cmux writes it again), `Claude turn N completed` once per assistant message with its tokens, text and reasoning as `run_progress`, each tool call as `function_call_requested` (`<tool> <json arguments>`), each tool result as `tool_progress` and `function_call_completed`, and every image in a tool result as a run screenshot. A permission request is relayed too: when the user's Claude settings ask before a call (an `ask` rule wins over the permission mode), the headless run cannot ask, cmux's wrapper puts the request in cmux's Feed (right sidebar, Ctrl-4) and as a notification, and waits about two minutes before the call counts as denied; the stream's `PermissionRequest` hook line becomes a `run_progress` warning "Claude is waiting for your approval to use <tool>", and `approvals.py` looks the request up in the Feed (`cmux rpc feed.list`, matched by Claude's session and the tool) and remembers it for the run. The console then shows **Allow once** and **Deny** on the run card; `POST /api/live/session/runs/{id}/approval` with `{mode: "once" | "deny"}` answers through `cmux rpc feed.permission.reply`, the call cmux's own Feed makes, and the stream's hook response becomes "Approval answered: allow" (or "Approval not answered in time"). Usage is counted per assistant message while Claude works, so a stopped run keeps its tokens; the closing line replaces those counts with Claude's own totals per model and its cost, which the cost panel uses for a model the price table does not price. A run fails when Claude exits without a result (its stderr is in `cmux/stderr.log`), ends in an error such as the turn limit, or its workspace is closed by hand. The backend must be able to reach cmux's socket, so it has to be started from a terminal inside cmux; the run uses the Claude login and Claude Code settings of that user. Both agents are built the way a stage is, from a typed input: `scenario_runtime` fills a `prompts.ActorInput` (the agent, the task, the session's `ActorInputs`, and for the desktop agent its worker mode and desktops) and `prompts.instructions(inputs)` renders it: the desktop agent's opening and a block per desktop, or the cmux agent's block (which points it at cmux Computer Use for app interfaces), then the same task rules, then the live context.

The instructions then say where to work: the user wants the task done efficiently and effectively, so tools that need no screen (bash, web search, a connected service's tools), usually the faster, are preferred when they can do a step, and a screen used when it is the faster way or necessary, in order: web pages in the browser tools; other apps on the remote desktop when the session has one; the user's Mac only when the task needs what is there (their accounts, files, apps' data), and then ask the user first and end the turn on that question. On the Zen monitor a remote-desktop button beside the browser one swaps the monitor to the remote desktop and back; while the agent's latest step is on it the monitor shows it anyway, live; **Take control** opens it full size, as the browser sheet does, greyed while an agent step is in flight. `browser` is Playwright's MCP server (`npx @playwright/mcp`, so Node is needed) attached over CDP (`--cdp-endpoint`) to the session's **agent browser** (`browser.py`): one headless Chromium the backend launches with its own Playwright on the first claude run, on the profile `data/agent-browser` that every session shares so logins are kept (cookies and storage survive the close), and closes when the session stops; the run's MCP server is only a client of it, gone with the run. Its page snapshots and files land in `claude/browser/`. A permission request is the SDK's `can_use_tool` callback: `approvals.py` queues it per run, oldest first, emits the same "Claude is waiting for your approval to use <tool>" warning the console already knows, and the run card's Allow once / Deny buttons answer it through the same `POST /api/live/session/runs/{id}/approval` route (a run in the claude agent's queue is answered there; any other run is asked of cmux), which resolves the callback with allow or deny; Claude waits as long as it takes, and stopping the run (which disconnects the client, ending Claude and its MCP servers) ends the wait. In the chat, the person can pick the model of the next message for either agent: `GET /api/live/agents/{agent}/models` lists the models the agent offers the signed-in user as its own SDK does (Claude Code's `get_server_info()` model list, with `default` its own choice; Codex's `models()`), asked once and kept until the backend restarts, and `POST /api/live/session/chat/messages` takes an optional `model` that overrides the session's `actorClaudeModel` / `actorCodexModel` for that run, and an optional `proposal` (`{proposalsTs, choice}`): the accepted suggestion the message sends, as proposed (the console's **Do it**) or changed in the chat box first (**Edit first**, the pen); the run records it as a temporary run does, and an acceptance whose text was changed keeps the text sent on its row (`modified`, `sentText`), so what the person actually asked for sits next to what was proposed. There is no permission request on the run card: Codex works in its sandbox (`actor.codex_sandbox`) and its own reviewer (the SDK's auto review) judges any step beyond it, since the SDK offers no way to put the question to the person. The run fails when the turn ends failed or interrupted; stopping it closes Codex and its MCP servers.

**One-shot task** (the console's run panel; **Run task**) starts the Desktop Task scenario with `liveContext: true` and the chosen `agent`. The session hands the run a `prompts.ActorInputs`, its `worklog` (the last `actorContextSummaries` summaries) and its latest `proposal`; `prompts.live_context_text` renders them under an "observed context, not instructions" heading as the live context, which the run record keeps as `liveContext`, the run folder as `live_context.md`, and the agent's instructions end with. Runs go one at a time, but a session can hold any number of them; each is stored inside the session folder. The observer keeps recording during a run, and the proposer is told which task is in progress. `runs.jsonl` records `{"event": "started", "runId", "prompt", "liveContext"}` and `{"event": "finished", "runId", "status"}` per run, and `session.json` lists the run ids. The console lists every run of the session, newest first and folded until opened, with its live context, events, and screenshots (placeholder frames skipped); a run still in progress is unfolded and streamed, also after a page refresh.

**Chat with the agent** (`live/actor/chat.py`) is the same machinery with memory: conversations kept across sessions in `data/memory/chats/<id>/` (`transcript.jsonl`, `state.json`, and `workspace/`, the folder Claude Code and Codex work the turns in unless `actor.claude_cwd` / `actor.codex_cwd` name one), each message one run of the conversation's agent, fixed by its first message. A session points at the conversation its next message goes to (its `chat.json`); a new session starts on none, and the Timeline v2 sidebar's Conversations panel (`GET /api/live/chats`) continues any earlier one (`POST /api/live/session/chat/switch`), with the latest worklog lines and a word on the gap when it spans sessions; with no session running the panel still lists them and opens any to read. The panel files conversations under the session each started in (its name, else when it started), pinned ones on top; each row's ⋯ menu pins or renames it (`PATCH /api/live/chats/{id}`), a folder's renames the session. Sessions from before the store kept `chat.jsonl` in their own folder: those conversations are listed (`legacy`, `viewOnly`) and readable in place, not continued. `POST /api/live/session/chat/messages` with `{text, agent, model?, proposal?, selectedTasks?}` composes the turn (`Chat.compose`): the first message is prefixed with the session's live context like a one-shot run; every later one with the worklog lines written since the previous message ("Observed since your previous message …", or that nothing was), so the agent learns what happened while it worked or the person was away. The context travels in the prompt, not in the instructions, so it stays in the agent's transcript; the run's `liveContext` and `live_context.md` keep it too, and the run detail carries `chat: {turn, resume, claudeSessionId, reply}`. For the cmux agent a later turn runs `claude -p --resume <session id>` (the id Claude's first stream line gave the previous turn), so Claude Code holds the conversation itself; the desktop agent is not wired to the chat yet. Chat turns are listed in `session.json` under `chatRuns` as well as `runs`, so the console shows them in the chat panel (each reply with its run card folded under it, the turn in progress streaming) and not in the Runs list; runs stay one at a time across both. The transcript is `chat.jsonl` in the session folder (the person's rows with the text, the context, how many lines it carried and, for a message the Timeline's **Ask Cue** built, `selectedTasks`: the task entries picked in the tray, `{taskId, title, text}` each, which the text quotes at its top, so the record tells them from what the person typed; the agent's with its reply and the run's end status), the state `chat.json` (conversation id, agent, turn, the worklog cursor the next context starts after, what to resume). `GET /api/live/session/chat` returns the current conversation, the lines the next message will carry, and the list of the session's conversations (id, agent, turns, start, first message); `?id=` reads an earlier one, read-only; `POST /api/live/session/chat/reset` starts a new one (the old rows stay on disk, each with its `chatId`). A stored session's conversations are read through `GET /api/live/sessions/{id}/chat[?id=]` and shown in the history view, each reply unfolding into its run, which is how a conversation is shown to someone later. **Accept → Chat** on a proposal records the accept and puts the proposal in the chat box.

### Storage Layout

```
data/sessions/<timestamp>/
  session.json               settings (wire view), usage and cost per model, run ids, stop reason, expiry
  snapshots.jsonl            observer rows: screen_changed, screen_unchanged, screenshot_taken, observer_paused, observer_started/stopped
  screenshots/               observer captures
  summaries.jsonl            worklog lines
  beliefs.jsonl              each belief update's ops, and the task list after it on a row whose ops would not rebuild it from the row before (a session's first, one after a rule fired or the operator edited)
  proposals.jsonl            ranked proposals
  live_model_calls.jsonl     every summarizer and proposer request and response
  feedback.jsonl             accept / reject decisions, each with what the proposer saw that round, condensed; an acceptance sent to the chat changed keeps the text sent (modified, sentText)
  summary_feedback.jsonl     flags on summaries
  runs.jsonl                 task run start and end markers
  runs/<run id>/             full artifacts of each task run started from the session
    cmux/                    a cmux run only: prompt.md, instructions.md, launch.sh, stream.jsonl (Claude Code's stream), stderr.log
    claude/                  a claude run only: instructions.md, stderr.log, browser/ (the browser's page snapshots and files)
    codex/                   a codex run only: instructions.md, browser/
  observer.log               observer subprocess output
```

Stored sessions from older versions are read with today's settings keys filled from the defaults (`normalize_record` in `storage/sessions.py`), and their stored proposal sets are lifted to the current record shape on read.

### Memory Across Sessions

```
data/memory/
  summaries.jsonl   every worklog line from every session, with its sessionId (the summarizer appends it)
  tasks.json        the current task list plus the belief updater's cursor into summaries.jsonl
  events.jsonl      every operation applied, with ts and sessionId
  feedback.jsonl    every accept / reject of a proposal, with what the proposer saw then in a few words (the proposer's feedback source)
  task_feedback.jsonl  every thumbs up / down on a task or an entry, with the reason when one was given
  stream/<date>.jsonl  every event of every kind, in order, in one envelope, one part per UTC day: the timeline (storage/stream.py)
  search.sqlite     the history index: the stream's worklog, chat, proposals and decisions in one full-text table (storage/search.py)
```

**The stream and the state.** Everything that happens is also appended to the stream, `data/memory/stream/<date>.jsonl`, one part per UTC day of the event's time, in one envelope, `{id, ts, kind, sessionId, callId, data}`, where `data` is the record exactly as its own file holds it: every observer row (`screen_changed`, a new read of the focused window; `screen_unchanged`; `screenshot_taken`, with the file name rather than the bytes; `observer_paused`, `observer_started`, `observer_stopped`), every stage output (`summary_written`, `belief_updated`, `proposals_made`, `preferences_updated`), task runs (`run_started`, `run_finished`), chat turns (`chat_message`, the person's; `chat_reply`, the agent's with how the turn ended: the proposer is shown the last hour's so it does not propose what was asked, the belief updater the window's so the agent's work counts), decisions as they happen (`proposal_accepted` or `proposal_rejected`, then `decision_digested` when the digest lands, `reject_reason_given` when one is given), flags (`task_flagged` as the flag stands after each click, `task_unflagged`, `summary_flagged`) and operator edits of the task list (`tasks_edited`, with the ops and the list after them). Every kind names what happened, as thing_pastTense. Nothing in the stream is edited later; the recorder process and the backend both append to it under a file lock. What is state-like keeps one file per kind, `tasks.json`, `feedback.jsonl`, `task_feedback.jsonl` and `preferences.md`, so a new stateful source gets its own file too; those and the per-session files remain what the console reads. Every belief update and operator edit carries the whole task list, about 30 KB today against some 7 MB of screen rows per hour of use; should the list ever grow large, carry the ops alone and fold. The stages read the stream: `Stream.window_at(start, end, session_id, lookback_days=…)` returns a `Window` that opens only the parts of the days it needs, whose `observations()`, `summaries()`, `worklog(minutes)`, `last_worklog(n)`, `tasks()` (the list at the end: the last belief update or operator edit before it that carried the list, with the ops of those after it replayed, `storage/ops.py`), `decisions(n)`, `undecided(m)` and `running()` are the inputs the summarizer, the belief updater and the proposer build from (the worklog, decisions and runs at most `session.stream_lookback_days` back; the task list however far back it was last carried), live (from the first new event to now) and in a replay (the bounds a model call recorded). Every row in `live_model_calls.jsonl` records `windowStart` and `windowEnd`, and the session's `session.json` the settings the calls ran with, so `python -m app.live.replay --session data/sessions/<id> --stage proposer` reruns those windows from the stream under the current `CUA_*` settings: adding a kind the stored call did not have is a settings change. `python -m app.live.storage.convert --data-root data` (backend stopped) rebuilds the stream from the per-kind files, for history recorded before the stream existed; it moves an existing `stream.jsonl` aside and deletes nothing.

The task list is what the proposer's `tasks` source shows. The operator can correct it from the live page behind its Edit button (tick or untick an entry, mark a task done or reopen it, rename it): `POST /api/live/tasks` with `{"ops": [...]}` holding `status`, `rename`, `update` (with `remove` entry numbers, or `reword` for open entries), `delete` and `restore` ops, the same ops the model's tools become plus `restore` (a task, or one entry by its number in the trash), applied under the same rules and logged in `events.jsonl` with `sessionId` `operator`; the response carries the visible list and the trash, which the console shows under the tasks with a Restore button in Edit mode. Outside Edit mode too, every task and entry carries a thumbs up and a thumbs down: `POST /api/live/tasks/feedback` with `{taskId, step?, verdict}` records the operator's verdict on the belief updater's work in `data/memory/task_feedback.jsonl` (an `id`, time, session, task id and title, entry number and text as shown, verdict). One record per task or entry: the other thumb updates that record (and drops its reason), the active thumb clicked again removes it (`DELETE /api/live/tasks/feedback/{id}`). A thumbs down offers a reason, optional and one click (`made up`, `duplicate`, `wrong level`, `already done`, or a few typed words) that `POST /api/live/tasks/feedback/reason` with `{flagId, reason}` writes onto the record. The console shows the active thumb and the reason next to each task and entry, matching an entry's flag by its text as well as its number, since numbers shift when an earlier entry is removed. Nothing on the list changes with a flag, a flag outlives a later delete of what it was on, and the preference updater (pipeline step 8) reads each flag as a reaction.

Every record also has an id of its own: `new_id()` (`storage/records.py`, 12 hex like a call's) is minted before the row is written, and the row's event in the stream reuses it, so a worklog line, a proposal set, a belief update, an observer row, a chat row, a run marker or a decision is one `id` in its own file and in `data/memory/stream/`; a prompt can show it and a model can cite it. Rows from before were given theirs by `python -m app.live.storage.backfill_ids --data-root data --write` (each row its event's id, matched by kind, session and `ts`; a row with no event, such as a chat row from before the chat was in the stream, a new one; the stream itself is never rewritten, since two cursors hold byte offsets into it; the newest session is skipped while it runs). Every piece of feedback can also be traced to the model call behind it by one id. Each call a live stage logs in `live_model_calls.jsonl` gets a generated `id`; the record it produced (`summaries.jsonl`, `beliefs.jsonl`, `proposals.jsonl`) carries it as `callId`, and so does every op the belief updater applied, in `data/memory/events.jsonl`. `MemoryStore.apply` stamps each task and entry it adds with the `callId` of the batch, so a flag copies the id of the call that added what it is on, and a decision on a proposal copies the id of the proposer call that made the set. An operator edit gets a generated id of its own, which appears on its ops in `events.jsonl` and on what it added. The full history of a task, every call that touched it, is the events log filtered by its id. Tasks from before ids were recorded carry none. Deleting a session does not remove its lines from memory. A `belief` replay uses a throwaway memory under the replay folder, built from that session's worklog alone; a `proposer` replay reads the task list as it was at each window from the session's `beliefs.jsonl`.

**The history index.** The proposer's inputs cover the session's last few worklog lines; what came before reaches it through the task list and a few decisions, which is not enough to know, say, which city's conference the flights are for. So the timer's proposer has one tool, `search_history` (defined once in `storage/search.py`, `TOOL` and `run_tool`, independent of any stage, so an agent can be given the same tool later; `proposer/propose.py` hands it to the model): keywords, all required and matched by word stem (a word may end in `*` for a prefix), or a case-insensitive regex, or both, within an optional time slice and, when asked, only some `kinds` (`worklog`, `chat`, `proposal`, `decision`; the first two unless the call says otherwise, since proposals are short lines and would rank high), and it gets the best matches with their date and time (local time; `since` and `until` are read as local time too, unless they carry a zone), a text once per kind; a kind that is not one of those or a regex that does not compile is rejected with why, and the model may call again. The model is told what the index holds (how many lines, back to when) and to search whenever its inputs may lack something, up to `proposer.search_rounds` times; the last allowed round is made with `tool_choice: none`, the tool still defined (a conversation holding tool calls must keep defining them on some providers), so it answers; should it call the tool anyway, the round ends with no proposals and the summary `(model output was not a JSON object)`, its searches kept on the record. Each round is a logged model call; the searches go on the proposal set as `searches` (the query, regex and kinds, the slice, the hit count, the first lines, or why the call was rejected), which the Timeline theme's drawer shows. The index, `data/memory/search.sqlite` (`storage/search.py`), is SQLite's FTS5 over the kinds worth searching (`summary_written`, `chat_message`, `chat_reply`, the tasks of `proposals_made`, `proposal_accepted`, `proposal_rejected`, a typed `reject_reason_given`), about 1.5% of the stream's bytes, never the screen rows. It is derived from the stream and never written to directly: it keeps a cursor into the stream and, before each search, indexes what was appended since, by the line heads, in milliseconds; missing, or of an older `VERSION`, it is rebuilt from the parts (about a second per 300 MB). `GET /api/live/history?q=…&regex=…&kinds=worklog,chat&since=…&until=…&limit=…` runs the same search, to try queries by hand.

**Citations.** Every line the proposer's prompt shows carries the record's id in front, `[a326a31b0884]`: worklog lines, decisions, chat turns (`utils/prompting.py`, `proposer/prompts.py`), search results (`Hit.line`), and tasks by their own ids. Each proposal answers with `evidence`, the ids it rests on, `[]` when it rests on the screen alone. Before the set is written, `cite()` (`proposer/propose.py`) keeps only ids the prompt showed, so a made-up id never reaches the record, and puts on the set as `cited` the cited records the console may not hold, the search results and the decisions from other sessions, each with its text and time. The idle trigger's proposals cite the same way, without searches. In the Timeline theme every proposal on a card has its own `why?`, which opens the drawer on that proposal alone: its task, its reason, and what it rests on as a row of chips, a glyph for the kind and the time, the text on hover. A chip for a record of this session opens that record and, while the suggestion is selected, the spine rings the cited marks and draws a dashed line from the suggestion to each; a chip for a worklog line from another session links to the Notes page landing on that line (`/v1/notes?session=…&id=…`), one for another session's decision to that session's History page, a task shows its title. The belief updater does not cite yet.

### HTTP Surface

Active session (`app/live/api.py`):

- `GET /api/live/session` → `{active, defaults, limits, session}`; `session` carries the record plus observer state, counts, tick counts, next tick times, and the latest proposal set.
- `POST /api/live/session` with a JSON object of request keys from the table → starts a session (`409` when one is active).
- `POST /api/live/settings` with the same JSON object → the session status: writes a provider's key or base URL to `.env` and the rest to `settings.yaml`, and reads both again as the next session's defaults; an empty body only reads them again (the settings page does that when it opens).
- `POST /api/live/settings/check` with the same JSON object → `{ok, checks[]}`: a one-word completion through the summarizer's and the proposer's endpoints and, when the desktop agent is set up, the task agent's Responses API endpoint, each with latency or the exact error, the belief updater's endpoint probed for parsed tool calls, the observer's macOS permissions, the cmux agent's reach to cmux (`cmux ping`) and the claude agent's `claude --version`, the codex agent's Codex login (the SDK's `account`) and `npx --version`, each when set up, and a price check: every configured model (the three stages and the desktop agent when it is set up; Claude Code reports its own cost) must have an entry in `app/configs/model_prices.json` or `CUA_MODEL_PRICES`, 0.0 for a self-hosted one, so the cost panel can always add it up. The start form's **Test configuration** button calls it.
- `POST /api/live/session/stop`, `POST /api/live/session/propose` (summarize what is pending, then run the proposer over it).
- `POST /api/live/session/tune` with any of `proposerIntervalS`, `proposerIdleTrigger`, `proposerIdleS`, `proposerIdleCooldownS`, `proposerDedupThreshold` → the status: the running session changes at once (the proposer's timer starts over on the new interval; a tick in flight finishes first) and `settings.yaml` keeps the value as the next sessions' default; `POST /api/live/session/idle-trigger` `{enabled, idleS}` is the same for the idle switch. Other keys are refused with `400`.
- `POST /api/live/session/pause`, `POST /api/live/session/resume` → the status. Paused, the session holds everything: the observer takes no looks (it reads the `observer.paused` flag file in the session folder), the three loops wait before their next tick (a model call already in flight finishes), `propose` and every run, a chat turn included, are refused with `409 live_session_paused`. The time limit counts running time only: the deadline (`expiresAt`) moves by as long as the pause lasted, so a 2-hour session gets 2 hours of running. A session resumed with under a minute left gets a minute, so a pause just before the limit does not end it the moment it resumes. The record carries `pausedAt` while paused and `pausedS`, the paused time in all; the stream gets a `session_paused` and a `session_resumed` event. Both routes are `409` when there is no session or it is already in that state.
- `GET /api/live/session/summaries?limit=`, `GET /api/live/session/proposals?limit=`, `GET /api/live/session/context` (the digest a run would receive), `GET /api/live/session/screenshots` (the stored screenshots, oldest first: `{ts, name, app, window}`), `GET /api/live/session/screenshots/{name}`, `GET /api/live/session/changes?limit=` (the belief ticks that applied `ops` or had a call held by the lookalike check (`warned`) or refused by the check (`rejected`), oldest first, with the `rounds` each took and `calls`, every tool call in order with its round, the op it asked for, whether it was applied and the result the model read; the timelines' task-update card shows each round's calls and the net result), `GET /api/live/history?q=&regex=&kinds=&since=&until=&limit=` (the history index the search tool reads, `kinds` comma-separated: `{hits: [{id, ts, kind, sessionId, text, line}]}`; 400 for an unknown kind or a regex that does not compile). The status's `latestScreenshot` names the newest screenshot and `latestSnapshot.visible` lists the other windows on screen.
- A run started with `proposal: {proposalsTs, choice}` on `POST /api/runs` carries that accepted proposal: the run record and the session's `runs.jsonl` marker keep it, so the run a proposal became can be found from the proposal.
- `GET /api/live/session/chat[?id=]` (with no session running it still answers, read-only: the conversation `id` names from the store, nothing current), `POST /api/live/session/chat/messages` (`{text, agent, model?, proposal?, selectedTasks?}`: one chat turn, started as a run and answered like `POST /api/runs`), `POST /api/live/session/chat/reset`, `POST /api/live/session/chat/switch` (`{id}`: continue a conversation, of this session or an earlier one; its state lives in the store, so the one left can be switched back to; `409` for a view-only one), `GET /api/live/chats` (every conversation, latest first, with `legacy` / `viewOnly` flags, the sessions it touched, the `title` the person gave it and whether it is `pinned`, plus `sessions`: those sessions' names by id), `PATCH /api/live/chats/{id}` (`{title?, pinned?}`: a display name in place of the first message, null or empty taking it away, and the pin that keeps it at the top of the sidebar; kept in `data/memory/chats/meta.json`), `GET /api/live/sessions/{id}/chat[?id=]`.
- `POST /api/live/session/proposals/feedback` `{proposalsTs, decision, choice?}`; `POST /api/live/session/summaries/feedback` `{summaryTs, comment?, verdict?}`.

Stored sessions: `GET /api/live/sessions?limit=&offset=&named=` (a page, newest first, `named` true or false keeping the sessions given a name or the rest; the History panel's ‹ › turn pages of 20 under its All / Named / Recent filter), `GET /api/live/sessions/{id}` (record, summaries, proposals), `PATCH /api/live/sessions/{id}` with `{"name": string | null}` (a display name saved in its `session.json`; the folder keeps the timestamp id), `DELETE /api/live/sessions/{id}` (removes the whole folder, runs included); both are 409 for the running session, and the same two feedback routes, the screenshot route, the screenshots and changes lists, and `GET /api/live/sessions/{id}/usage` (the session's cost rows) under `/api/live/sessions/{id}/`.

Cost: `GET /api/live/usage?days=` → `{all, recent, days, session}`, each a list of rows per model and module (summarizer, belief updater, proposer, agent) with the token counters of `app/usage.py` and `costUsd` when the price table knows the model: `all` over every stored session, `recent` over the last `days` days, `session` for the running one (null otherwise). Computed from the stage files and `run.json` on each call; the console's Cost panel shows `session` during a session and `all` plus `recent` between sessions.

Disk: `GET /api/live/disk` → `{root, free, sessions, rest}` (`storage/disk.py`), all in bytes: `root` is the data folder and `free` what its volume has left; `sessions` lists each session folder, oldest first, as `{id, name, screenshots, modelCalls, runs, screenReads, other}` (the observer's pictures, `live_model_calls.jsonl`, the files of its runs, `snapshots.jsonl`, and the small records together); `rest` is the folder beside its sessions as `{memory, agentBrowser, other}`. The parts add up to the folder. Summed from the files on each call. The Usage page's Disk view (the Cost / Disk switch at its top) shows them by kind and by session, largest first, each session a link to its History page, where it can be deleted.

Compressing sessions (`storage/pack.py`): `POST /api/live/disk/compress` `{ids}` starts packing stored sessions' two large parts in place, and `POST /api/live/disk/restore` `{ids}` starts writing compressed ones back as they were (202; never the running session, one job at a time); both answer with the disk report, whose `packing` (`{total, done, sessions, finished, failed, running}`, bytes read of bytes to read, and per failed session why) says how far along they are. The work is the backend's, not the page's: `Packing` runs three sessions at a time in daemon threads (about a core and under a gigabyte each), no step holds the interpreter for long (xz, the PNG codec and SHA-256 release it; the log is gone through a line at a time), so a running session goes on as before, and any page that reads the report shows the progress. The screenshots: a PNG is compressed on its own, so the files do not shrink in an archive, but their pixels do, one screen being much like the one before. The pixels are packed 32 screenshots to a block, each block one xz stream in `screenshots.pack`, with `screenshots.pack.json` beside it (per file its block, where its pixels are there, its size, mode and SHA-256; its presence is what marks the session compressed). A PNG written back from its pixels is the file the observer wrote, byte for byte, which is checked for every file, from the pack as it will be read, before the file is removed; a file that does not come back identical stays a file. The model-call log, which repeats the screenshots as base64 data URLs, is kept as `live_model_calls.jsonl.xz` with every URL that `encode_screenshot` derives from a stored screenshot replaced by `screenshot:<max side>:<SHA-256 of the file>`, and it too is checked to come back as it was, from what was packed, before the file is removed (a log that already reads like such a reference keeps its URLs: `calls.plain` in the index); rows logged while it was being packed stay in `live_model_calls.jsonl`. The pack, its index and the packed log are flushed to the disk before anything they stand in for is removed. A compressed session stays readable: the screenshot routes read one picture out of its block (the block last read is kept, for its neighbours), and a decision on an old suggestion reads the logged call and its pictures through the pack; `python -m app.live.replay` asks for a restore first, as does anything that reads the PNG files themselves. A restore checks every SHA-256 and stops, the pack kept, when a file would differ, which only another Pillow than the one that packed it can cause (the pixels are the same either way; the index records the version). A backend stopped mid-way leaves a session as it was or compressed. The Usage page's Disk view (remembered as the view last shown) has a first column of tick boxes, one in its header for every session, "Older than 1 week" and "Older than 3 weeks" to tick the sessions not yet compressed by age, Compress and Restore buttons for the ticked ones (each takes those it applies to), a progress bar with "N of M" while they are worked through (the report read again every two seconds), and a mark in the last column on a compressed session.

Task runs use the ordinary run routes in `app/api.py`; `POST /api/runs` with `liveContext: true` ties the run to the active session.

## Bedrock Tokens From AWS Credentials

`OPENAI_API_KEY=aws-bedrock-token-generator` makes `resolve_api_key` in `app/credentials.py` mint a bearer token with the `aws-bedrock-token-generator` package from the default AWS credential chain (`aws configure`, `AWS_PROFILE`, or environment variables) for the region parsed from `OPENAI_BASE_URL`. Tokens are cached and minted again after six hours. The task agent, the summarizer, and the proposer all resolve keys the same way; a literal key passes through unchanged. Bedrock's OpenAI-compatible endpoint also needs `OPENAI_PROJECT_ID`, which the OpenAI SDK sends as the `OpenAI-Project` header.
